# 01. 아키텍처 — 시나리오를 가드레일로 쓰는 RAG

## 0. 설계 원칙

1. **생성형은 사실의 출처가 아니다.** 사실은 코퍼스에서만 나온다. LLM은 이해·검색질의생성·재표현만 한다.
2. **위험도가 다른 질문을 같은 경로로 보내지 않는다.** 진료시간 안내와 "이 약 먹어도 되나요"는 같은 파이프라인이면 안 된다.
3. **모르면 안 답한다.** abstain은 실패가 아니라 정상 출력이다.
4. **시나리오는 폐기하지 않는다.** 두 가지 역할로 재활용한다 — (a) 근거 코퍼스, (b) 폴백 목적지.

## 1. 전체 흐름

```
사용자 발화
   │
   ├─ [0] 안전 인터럽트         응급 키워드 / 자해 / PII → 즉시 전용 응답, 파이프라인 종료
   │
   ├─ [1] 질의 정규화            멀티턴 문맥 병합, 대명사·생략 복원 → self-contained query
   │
   ├─ [2] 리스크 티어 라우터     의도 분류 + 위험도 판정
   │        ├─ TIER-A (의료판단)      → 생성 금지. 고정 문구 + 진료/상담 안내
   │        ├─ TIER-B (절차·행정 안내) → RAG 생성 허용  ◀ 이 프로젝트의 주 전장
   │        └─ TIER-C (앱 기능·잡담)   → 기존 시나리오 / 소형 응답
   │
   ├─ [3] 검색 (TIER-B)          Hybrid: BM25 + Dense → Rerank → top-k
   │        └─ 근거 점수 임계 미달 → abstain 경로로 이탈
   │
   ├─ [4] 근거 강제 생성         "제공된 근거로만 답할 것 + 문장별 출처 태깅 + 부족하면 부족하다고 말할 것"
   │
   ├─ [5] 검증 게이트            ① claim ↔ 근거 대조(entailment)
   │                             ② 금칙 표현 필터(진단/처방/단정)
   │                             ③ 숫자·날짜·연락처 원문 일치 검사
   │        └─ 실패 → 재생성 1회 → 또 실패 → abstain
   │
   └─ [6] 출력                   답변 + 출처 + (필요 시) 상담원 연결 버튼
```

## 2. 시나리오 → 코퍼스 변환 (이 프로젝트의 핵심 기여)

기존 시나리오 트리를 그대로 인덱싱하지 않고, **노드를 QA 단위로 평탄화**한다.

```
scenario node  ──▶  corpus record
{
  id:            "SC-예약-변경-001",
  question_forms: ["예약 변경", "예약 바꾸고 싶어요", ...],   # 기존 분기 라벨 + LLM 증강
  canonical_answer: "<법무/의료진 검수 완료 원문>",
  entities:      {dept: null, channel: ["app","tel"]},
  risk_tier:     "B",
  source:        {type: "scenario", version: "2026-03", owner: "운영팀"},
  verbatim_required: false      # true면 재표현 금지, 원문 그대로 출력
}
```

포인트:
- `verbatim_required: true` 인 레코드(검사 전 금식 지침, 수납 금액, 법적 고지)는 **LLM이 문장을 바꾸지 못한다.** 검색해서 원문을 그대로 붙인다. → 여기서 할루시네이션 확률이 0이 된다.
- `false` 인 레코드만 재표현 허용 → 여기서 "AI 같은" 자연스러움이 나온다.
- 이 플래그 하나가 "안전 vs 체감 지능" 트레이드오프의 조절 노브가 된다.

## 3. 코퍼스 소스 (계층)

| 계층 | 소스 | 신뢰도 | 재표현 |
|---|---|---|---|
| L0 | 시나리오 확정 답변 | 최상 | 조건부 |
| L1 | 병원 공개 안내 페이지 (진료시간, 오시는 길, 검진 패키지) | 상 | 허용 |
| L2 | 앱 사용 매뉴얼 / FAQ | 상 | 허용 |
| L3 | 부서 내부 안내문(정제 후) | 중 | 허용 |
| ✗ | 일반 의학 웹문서 | 사용 금지 | — |

검색 시 L0가 히트하면 **L0를 우선 채택**하는 소스 우선순위 규칙을 둔다.

## 4. 컴포넌트별 기술 선택 후보

| 컴포넌트 | 후보 | 비고 |
|---|---|---|
| 청킹 | 문서구조 기반(heading) + QA 단위 | 고정 길이 청킹은 병원 안내문에 부적합 |
| Sparse | BM25 (Kiwi/Mecab 형태소 토크나이저) | 한국어 병원 용어·고유명사에 강함 |
| Dense | 한국어 임베딩 모델 비교 실험 필요 | P1에서 벤치 |
| Rerank | cross-encoder reranker | top-50 → top-5 |
| Vector store | 초기 FAISS(로컬) → 운영은 pgvector/OpenSearch | 병원 환경은 온프렘 가능성 |
| Generator | Claude (Opus/Sonnet 5) | 근거강제·거절 준수 성능 우선 |
| Verifier | 소형/저비용 모델 + 규칙 필터 | 비용·지연 고려 |

## 5. 왜 이 구조가 발주처 설득에 유리한가

- 생성형을 "쓰냐 마냐"의 이진 논쟁을 **티어별 허용 범위 협의**로 바꾼다.
- `verbatim_required` 플래그로 "이 문장은 절대 안 바뀝니다"를 문서로 보여줄 수 있다.
- abstain·에스컬레이션이 기본 동작이므로, 최악의 경우 **현재 시나리오 챗봇과 동일한 안전성**으로 수렴한다.
  → 다운사이드가 없다는 논증이 가능하다. 이게 승인의 핵심 논리다.
