STEP 1설치
$ npm install -g @anthropic-ai/claude-code
✓다 끝나면 claude --version 을 쳐서 버전이 찍히면 성공입니다.
1~2분 걸립니다. 돌아가는 동안 다음 얘기를 이어 가겠습니다.
STEP 2저장소에서 실행 · 로그인
$ cd ~/Projects/my-repo $ claude
✓브라우저가 열리면 승인하고 터미널로 돌아옵니다. 프롬프트가 뜨면 성공입니다.
브라우저가 안 열리면 터미널에 찍힌 URL 을 직접 복사해서 여시면 됩니다.
STEP 3진짜 도는지 확인
> 이 저장소가 무슨 프로젝트인지 한 줄로 알려 줘
✓파일을 몇 개 읽고 한 줄로 답하면 설치 끝입니다.
읽기만 하는 요청이라 아무것도 안 바뀝니다. 첫 확인용으로 안전합니다.
여기까지가 «설치» 입니다. 지금부터 나오는 건 전부 «설정» 이고, 안 해도 돌아갑니다 — 다만 다음 장 네 가지는 5분이면 되고 이후가 크게 달라집니다.

Session 1 · 01

왜 터미널인가

웹·데스크톱 앱도 훌륭합니다. CLI 를 쓰는 이유는 «성능» 이 아니라 접근권입니다.

파일

내 디스크를 그대로 본다

업로드가 없습니다. 저장소 전체가 작업 대상이고, 고친 결과가 곧 워킹 트리에 남습니다.

git

브랜치·워크트리 위에서 돈다

커밋·병합·푸시가 대화 안에 들어옵니다. 되돌리기가 «다시 물어보기» 가 아니라 git 입니다.

훅

내가 만든 코드가 끼어든다

오늘의 핵심입니다. 도구 호출 전후에 내 스크립트를 걸 수 있는 건 CLI 뿐입니다.

CLI 를 고르는 순간 얻는 것은 속도가 아니라 «규칙을 강제할 자리» 입니다. 세션 1의 나머지는 전부 이 자리를 어떻게 쓰느냐입니다.

Session 1 · 04 — 부품 목록

열쇠는 다섯 개뿐입니다

Claude Code 를 «확장» 하는 방법은 이게 전부입니다. 뒤에 나올 하네스는 이 다섯을 조합한 것입니다.

  • CLAUDE.md항상 읽히는 지시문. 전역(~/.claude) → 저장소 → 하위 폴더 순으로 겹칩니다. 규칙의 «말» 이 사는 곳.
  • 스킬 / 슬래시 명령부를 때만 읽히는 절차서. 상시 지시문에 다 넣으면 컨텍스트가 터지므로, 무거운 절차는 스킬로 빼고 이름으로 부릅니다.
  • 서브에이전트별도 컨텍스트를 가진 일꾼. 조사·검증처럼 «읽은 것을 다 데려올 필요 없는» 일을 떼어 보냅니다. 결론만 돌아옵니다.
  • MCP바깥 세계와의 배선. 이슈 트래커·드라이브·브라우저·캘린더. 티켓 읽기와 코멘트 달기에 매일 씁니다.
  • 훅 (hooks)내 코드가 끼어드는 자리. 세션 시작·도구 호출 전후·응답 종료에 스크립트를 겁니다. 유일하게 강제력이 있는 부품입니다.

Session 1 · 05 — 환경 세팅

권한 모드와 안전선

«매번 확인» 은 안전하지만 느리고, 느리면 사람이 규칙을 끕니다. 그래서 확인을 줄이되 가드를 늘리는 쪽으로 갑니다.

  • default쓰기·명령마다 확인. 처음 며칠은 이걸로 감을 잡습니다.
  • acceptEdits파일 편집은 자동 승인, 명령은 확인. 실무 기본값으로 좋습니다.
  • plan읽기만 하고 계획을 세웁니다. 큰 작업 착수 전에.
  • bypassPermissions확인 없이 진행. 가드를 갖춘 저장소에서만 씁니다.
주의

bypass 는 «가드가 있을 때» 의 선택지입니다

확인 프롬프트를 없앤다는 건 판단을 사람에서 코드로 옮긴다는 뜻입니다. 옮길 코드가 없으면 그냥 무방비입니다.

우리 저장소가 bypass 로 도는 이유는 훅 6종 + pre-commit 8종이 그 판단을 대신하기 때문입니다. 순서를 거꾸로 하지 마세요.

덧붙여, 기본 확인을 줄일수록 «무엇을 읽히는가» 가 위험해집니다. 외부 저장소·이슈 본문·웹 페이지는 전부 프롬프트 주입 경로입니다.

Session 1 · 07 — 하네스 엔지니어링

하네스란 무엇인가

모델은 부품입니다. 하네스는 그 부품을 붙잡는 배선 — 무엇을 읽히고, 무엇을 못 하게 하고, 무엇을 되돌릴지 정하는 층입니다.

프롬프트 엔지니어링은 더 잘 말하는 법을 다룹니다. 하네스 엔지니어링은 말이 지켜지게 만드는 법을 다룹니다. 같은 모델로 결과가 갈리는 지점은 대부분 후자입니다.

한 문장으로: «규칙을 프롬프트에 적는 대신, 검사하는 코드로 옮긴다.»
규칙이 프롬프트 텍스트로만 존재하면 세션마다 지켜지기도 하고 안 지켜지기도 한다. — .claude/hooks/routing-guard.py 머리 주석
규칙은 2026-08-17 문서에 들어갔지만, 검사하는 훅은 없었다.

가드를 세울 때의 세 가지

여기서 제일 많이 데였습니다. 가드 자체가 버그를 만듭니다.

  1. 01정말 깨졌는지 «먼저» 확인한다. 순서를 바꾸면 — 게이트를 먼저 돌리면 — 깨지지도 않은 것을 보고 「게이트가 못 잡는다」로 읽습니다. 실제로 그럴 뻔했습니다.
  2. 02정탐과 오탐을 둘 다 본다. 오탐이 정탐 실패보다 비쌉니다. 막힌 사람이 게이트를 꺼 버리면 정탐도 같이 사라집니다. 오탐 하나가 세션 하나의 하루치 작업을 인질로 잡은 적이 있습니다.
  3. 03게이트가 «무엇을 볼 수 없는지» 도 적는다. 셸 동기 검사가 「빌더 출력 == 셸」만 보느라, 둘이 똑같이 깨진 경우를 통과시켰습니다. 그 자리는 검사 목록에 아예 없었습니다.
가드도 낡습니다. 워크트리에서 훅을 돌리면 «그 트리의 훅 사본» 이 돕니다. 19커밋 뒤처진 검사기가 정상 커밋을 거부했고, 108커밋 뒤처진 설정으로 리허설해 틀린 결론을 냈습니다 — 재는 자[尺]가 낡은 경우라 「세는 법」 규칙으로는 안 걸립니다.

원칙 01 / 06

정본을 먼저 정한다

같은 사실이 두 곳에 적히는 순간, 둘은 반드시 갈라집니다. 그래서 어느 파일이 정답인지부터 못 박습니다.

  • 코어 데이터 모델엔티티·필드의 정본은 arch-core-data-model.md 한 곳. 4곳에 흩어져 있던 걸 병합해 만들었습니다.
  • 내비게이션좌측 메뉴의 권위 정의는 내비게이션 정책 문서 §1 한 곳. 화면 코드 5개의 NAV_ITEMS 는 전부 사본입니다.
  • 디자인 토큰값의 정본은 scripts/tokens.py 한 곳. 화면 코드는 주입된 전역 객체로 받아 씁니다 — hex 를 직접 쓰지 않습니다.
  • 담당 라우팅slug ↔ 폴더 표의 정본은 routing.json. 훅도 티켓 디스패처도 이 파일만 읽습니다.
왜 이게 하네스인가

정본이 정해지면 가드를 걸 수 있습니다

「토큰 값은 여기서만 고친다」는 말입니다. 그런데 정본이 한 곳이면, ds-token-guard 가 «새로 추가된 줄에 구 팔레트 hex 가 있는가» 를 기계적으로 물을 수 있습니다.

정본을 안 정하면 검사할 대상이 없어서, 규칙이 영영 말로만 남습니다.

원칙 02 / 06

변경은 «점» 이 아니라 «파장» 이다

스펙 한 줄을 고치면 IA·유저플로우·데이터모델·화면정책이 함께 움직입니다. 그 파장을 사람 기억이 아니라 표가 계산합니다.

변경 유형 분류→ Impact Matrix 조회→ 영향 문서 목록 추출→ 고정 순서로 업데이트→ 완결성 체크리스트
고정 순서

순서를 건너뛰지 않습니다

arch-ia → arch-user-journey → arch-user-flow → arch-data-model → arch-ai-data-spec → screen-*.policy

계층이 위에서 아래로 흐르기 때문입니다. 데이터모델을 먼저 고치면 IA 와 어긋난 채로 굳습니다.

완결성 검사

정책서는 항목으로 잽니다

접근 조건(권한+상태) · 컴포넌트 표시 조건 · 로딩/빈/에러 상태 · 모든 버튼의 트리거→결과 · API 시점과 실패 처리 · 역할별 뷰 차이 · 엣지케이스 3개 이상.

AI 화면이면 4항목 추가. 「잘 썼다」가 아니라 「빠진 게 있다/없다」로 판정합니다.

원칙 03 / 06

한 저장소, 스물다섯 개의 손

기획 영역마다 git worktree 를 하나씩 두고, 각 워크트리에 세션이 상시로 붙어 있습니다. 결제 영역 세션과 관리자 영역 세션이 동시에 다른 파일을 고칩니다.

  • 왜 브랜치가 아니라 워크트리브랜치는 한 번에 하나만 체크아웃됩니다. 워크트리는 디렉터리가 25개라 세션 25개가 진짜로 동시에 돕니다.
  • 누가 어디를 맡나routing.json 의 slug ↔ 폴더 표가 유일한 근거입니다. 티켓 디스패처도, 훅도 같은 표를 읽습니다.
  • 메인은 무엇을 하나저장소 설정·빌드 산출물·병합 루프. 기획 파일은 손대지 않습니다 — routing-guard 가 실제로 막습니다.
실제 사고

이 규칙이 생긴 사고

메인 세션이 워크트리에 들어가 파일을 고쳤습니다. 진입 시점 git status 는 깨끗했습니다 — 동시 편집은 그 뒤에 시작되니까요.

그 워크트리 세션의 다른 작업이 같은 두 파일에 섞였고, 분리 커밋이 불가능해져 남의 미완성 작업이 함께 커밋됐습니다.

교훈: 「지금 깨끗하다」는 안전 신호가 아닙니다. 동시성 문제는 관측 이후에 생깁니다.

원칙 04 / 06

인계는 도구가 강제한다

세션 25개가 돌면 «넘기기» 가 일의 절반이 됩니다. 그래서 인계도 손이 아니라 스크립트로 합니다.

# slug ↔ 담당 폴더 표
python3 scripts/handoff.py --list

# 인계 (근거 스탬프 없으면 전송 거부)
python3 scripts/handoff.py checkout \
  --title "환불 정책 §3 정정" \
  --brief-file brief.md

# 보낼 내용만 확인
python3 scripts/handoff.py checkout … --dry-run
  • 근거 스탬프 강제브리핑에 출처가 없으면 전송을 거부합니다. 하루에 인계문 3건이 받는 쪽 실제 상태와 어긋난 뒤 세웠습니다.
  • 중복 감지직전과 같은 slug+같은 내용이면 경고. 한 세션이 같은 인계문을 8회 받은 날이 있었습니다.
  • 발신자 명시누가 보냈는지·어디로 회신할지를 박습니다. 익명이라 「이미 했다」고 알릴 수조차 없었던 게 중복의 진짜 원인이었습니다.
  • 뒤처짐 경고받는 워크트리의 규칙·게이트가 몇 커밋 뒤처졌는지 자동으로 붙입니다.

원칙 05 / 06

내가 하지 않은 확인을 한 것처럼 적지 않는다

이 저장소가 가장 많이, 가장 여러 얼굴로 데인 병입니다. AI 로 일할 때 특히 잘 납니다 — 그럴듯한 문장이 관측처럼 읽히기 때문입니다.

안 센 값

「컨트롤러 46개 전수 확인」

기획서 6종 이력에 근거로 박혔는데, 우리는 컨트롤러를 세어 본 적이 없습니다. 카드 본문 표현을 옮긴 것이고 실제는 58개였습니다.

좁은 검색

「잔존 0건」

workspaces/:wsId 로만 검색한 결과였습니다. :id·:workspaceId 변종이 16파일에 남아 있었습니다.

어긋난 단위

「읽는 유일한 폴더」

실제로 확인된 건 엔티티 전체를 읽는 유일한 폴더였습니다. 필드 단위로는 다른 폴더도 읽었고, 그 결과 인계에서 한 폴더가 빠졌습니다.

그래서 「전수 확인」류 주장에는 «세는 법» 셋을 함께 적습니다 — 무엇을 · 어느 단위로 · 어떻게(도구·검색어). 다음 사람이 값을 믿는 대신 다시 셀 수 있어야 합니다. 세는 값과 세는 법 중 오래 쓰이는 건 세는 법입니다 — 값은 다음 커밋에 낡습니다.

원칙 06 / 06

50%에서 끊는다

긴 세션의 진짜 위험은 «느려짐» 이 아니라, 자동 압축이 「지금 하던 일」을 요약된 기억으로 바꿔 놓는 것입니다. 원칙 05의 병이 컨텍스트 안에서 재현되는 자리입니다.

50% 도달→ 하던 한 가지만 마감→ 인계 카드→ /clear→ 새 세션이 카드만 이어받음
50%인 이유: 아직 스스로 무엇을 넘길지 고를 수 있는 시점이기 때문입니다. 압축은 아무 데서나 끼어듭니다.
카드에 쓰는 것쓰지 않는 것
지금 하던 일 — 끝나지 않은 한 가지끝난 일 · 오늘 한 일 목록
다음 한 걸음 — 처음 할 행동 하나계획 전체 · 로드맵
근거 — 커밋 SHA · 「확인: … (날짜)」기억으로 쓴 상태 주장
넘기지 않는 것 — 일부러 뺀 것—

끝난 일은 넘기지 않습니다. 넘겨야 할 만큼 중요하면 그건 카드가 아니라 커밋·문서·티켓 코멘트에 있어야 합니다.
