| | 주장 | 함의 |

# A. 하네스 엔지니어링 플로우

## A-1. 한 턴에서 코드가 끼어들 수 있는 5지점

```
세션 시작                                                            응답 완료
   │                                                                    │
   ▼                                                                    ▼
[SessionStart] ──▶ [PreToolUse] ──▶ 도구 실행 ──▶ [PostToolUse] ──▶ [Stop]
   규칙 주입          도구 차단                      상태 알림          응답 반려
   (넣는 자리)        (막는 자리)                    (넣는 자리)        (막는 자리)
                                                          │
                                                   [SubagentStop]
                                                    보고 반려
```

- **PreToolUse** = `permissionDecision: deny` 로 **도구 호출 자체를 거부**
- **Stop = 가장 강한 자리.** 응답을 반려하면 그 턴이 끝나지 않는다 → 「다시 쓰라」가 **요청이 아니라 조건**이 된다
- 초록(주입) / 주황(차단)의 구분이 설계의 핵심: 넣을 것과 막을 것을 섞지 않는다

## A-2. 규칙은 4층, 아래가 위를 이긴다

```
1층  ECC 플러그인            남이 검증한 기본기 (에이전트·스킬·언어별 규칙)
2층  ~/.claude/CLAUDE.md     내 개인 작업 방식 (말투·경로·컨텍스트 50% 인계)
3층  저장소 CLAUDE.md        이 저장소에서만 참인 것 (라우팅·절대규칙·사고 기록)
4층  .claude/hooks/ + lefthook   위 세 층을 실제로 검사하는 코드   ◀ 유일하게 강제력
     └ 훅 6종 + pre-commit 8종, 각각 테스트 파일 동반
```

**「저장소에 커밋된 규칙이 메모리를 이긴다」** — 두 세션이 같은 메모리의 서로 다른 시점 사본으로 정반대로 알았던 사고 이후, 결정은 전부 커밋.

**ECC = Everything Claude Code.** 오픈소스 플러그인 (에이전트 38 · 스킬 156 · 레거시 명령 72).
```
/plugin marketplace add affaan-m/everything-claude-code
/plugin install ecc@ecc
```

## A-3. 가드를 만드는 절차 (이게 실제 플로우)

```
① 사고가 난다            ── 전부 여기서 시작. 미리 설계한 가드는 하나도 없다
        │
② 정말 깨졌는지 먼저 확인  ── 순서를 바꾸면(게이트 먼저 돌리면) 깨지지도 않은 걸 보고
        │                    「게이트가 못 잡는다」로 오독한다
③ CLAUDE.md 에 규칙 + «왜» ── 규칙만 적으면 다음 사람이 지운다. 사고 기록이 붙어야 살아남는다
        │
④ 훅으로 옮긴다            ── 5지점 중 하나 선택. 차단이면 PreToolUse/Stop
        │
⑤ 정탐·오탐 둘 다 본다     ── 오탐이 정탐 실패보다 비싸다
        │                    (막힌 사람이 게이트를 끄면 정탐도 같이 사라진다)
⑥ «못 보는 것» 을 적는다   ── 검사 범위 밖을 문서화. 안 적으면 통과를 성공으로 착각한다
```

### 가드 3원칙 (여기서 제일 많이 데였다고 명시)

1. **정말 깨졌는지 «먼저» 확인** — 순서를 거꾸로 하면 잘못된 결론
2. **정탐과 오탐을 둘 다** — 오탐 하나가 세션 하나의 하루치를 인질로 잡은 적 있음
3. **게이트가 «무엇을 볼 수 없는지» 도 적는다** — 「빌더 출력 == 셸」만 보다가 **둘이 똑같이 깨진 경우**를 통과시킴

### 가드도 낡는다

워크트리에서 훅을 돌리면 «그 트리의 훅 사본» 이 돈다. 19커밋 뒤처진 검사기가 정상 커밋을 거부, 108커밋 뒤처진 설정으로 리허설해 틀린 결론. → **재는 자[尺]가 낡은 경우**라 「세는 법」 규칙으로는 안 걸린다.

## A-4. 실제 가드 카탈로그 (7종) — 각각이 특정 사고를 가리킨다

| 가드 | 지점 | 막는 것 | 사고 |
|---|---|---|---|
| `routing-guard` | PreToolUse | 메인에서 남의 담당 기획 파일 수정 | 두 세션 동시 편집 → 분리 커밋 불가 |
| `ds-guard` / `ds-session` | PreToolUse · SessionStart | 실측 근거 없이 화면 그리기 | 새 탭 통째로 만들었는데 가드가 한 번도 안 울음 |
| `honorific-guard` | Stop · SubagentStop | 반말 응답 → **턴을 끝내지 않음** | 말투 규칙이 문서에만 있어 세션마다 달랐음 |
| `ctx-relay-guard` | PostToolUse · Stop | 컨텍스트 50% 초과 후 인계 카드 없이 종료 | 자동 압축이 「지금 하던 일」을 요약 기억으로 바꿈 |
| `shared-index-guard` `main-index-guard` | PreToolUse · pre-commit | 남의 staged 파일 · 남의 MERGE_HEAD 위 커밋 | 메인 공유하며 남의 변경이 딸려 옴 |
| `ds-newscreen-guard` | pre-commit | 근거 인용 없는 새 화면 커밋 | 신규 «파일» 만 보다가 기존 파일 안의 새 화면을 놓침 |
| `stale-artifact-guard` | pre-push | 낡은 빌드 산출물 푸시 | 68커밋 뒤처진 트리에서 39커밋 분이 사라질 뻔 |

## A-5. 차단 메시지의 형태 — 「거부」가 아니라 「전환」

```
PreToolUse · routing-guard.py · permissionDecision: deny

메인 체크아웃에서 기획 파일을 고치려 했다 — CLAUDE.md STEP 0 위반.
  대상   : docs/specs/checkout/spec-checkout.md
  담당   : checkout (결제 영역)
  워크트리: ~/worktrees/checkout
  이 파일에는 그 워크트리의 담당 세션이 붙어 있다. 메인에서 고치면
  동시편집이 되어 분리 커밋이 불가능해진다.
```

**담당 slug · 워크트리 경로 · 다음 절차까지 붙여야 우회하지 않는다.** 방해물이 되는 순간 사람은 훅을 끈다.

## A-6. 권한 모드 — 순서를 거꾸로 하지 말 것

```
default ──▶ acceptEdits ──▶ (가드 완비 후) bypassPermissions
매번 확인    편집 자동승인        확인 없이 진행
             명령은 확인
```

> 확인 프롬프트를 없앤다는 건 **판단을 사람에서 코드로 옮긴다**는 뜻. 옮길 코드가 없으면 그냥 무방비.

덱의 저장소가 bypass 로 도는 이유 = 훅 6종 + pre-commit 8종이 그 판단을 대신하기 때문.

# B. Claude 자동화 플로우

## B-1. 회의 녹음 → 문서 (지금도 도는 파이프라인)

```
기획 미팅 ──▶ 전사 ──▶ 회의록 .md ──▶ ■ 멈춤 ──▶ 반영 대상을 번호로 제시
 구두 결정   transcript   위키 커밋                  1 · 2 · 3 …
                                                        │
                                              사람이 고름 "1번 3번만"
                                                        │
                                                        ▼
                                              다섯 벌 작성 + 연쇄
```

**«여기서 멈춥니다» 가 설계의 핵심.** 회의에서 나온 말이 전부 결정은 아니다 → 번호로 제시하고 **사람이 고른 것만** 반영.

세 가지 이득:
1. **구두 결정이 증발하지 않는다** — 문서로 안 옮겨진 결정은 «없던 일». 전사가 남으면 최소한 "정했는데 안 옮겼다"는 걸 안다
2. **결정의 출처가 소급된다** — 각 절에 «어느 회의의 어떤 발언» 을 달 수 있다 → 「이거 왜 이렇게 됐죠?」에 답이 있다
3. **한 번 멈춘다** — 사람의 선택이 파이프라인 안에 들어간다

> 사람이 한 일 = 회의하고, 녹음 버튼을 누른 것.
> 요점은 «AI로 문서를 뽑았다»가 아니라 **구두 결정이 그날 안에 파일이 됐다**는 것. 사흘 뒤 정리하면 그건 기억이지 기록이 아니다.

## B-2. 착수 전 3분 — 네 곳 조사

```
① 폴더 정본        그 기능의 기존 spec·policy → 있으면 «신규»가 아니라 «업데이트»
② 전역 문서        코어 데이터모델·내비게이션 정책 → 기능 결정처럼 보이는 게 실은 전역 결정
③ 관련 티켓 코멘트  문서엔 없지만 남이 카드에 적어둔 것
④ 그 결정을 받은 사람  어느 문서에도 없이 대화에만 있을 수 있다 (검색이 아니라 물어보기 → 잘 빠진다)
```

### 「미확인」과 「미조사」를 가른다 ← 가장 중요한 구분

- **미확인** = 찾아봤고 없었다
- **미조사** = 안 찾아봤다

둘을 섞어 「미정」이라 쓰면 **받는 쪽이 이미 있는 답을 다시 만든다.**

```
확인 : 정책 §1.2.4 · 스펙 §6.1 을 찾았고 없었다 (2026-08-25)
미조사 : 코어 데이터모델 · 관련 티켓은 보지 않았다
```

## B-3. 문서 다섯 벌 = 질문 다섯 개

문서를 «종류»로 외우면 매번 "뭘 써야 하지"로 시작한다. **각 문서가 답하는 질문 하나**로 기억하면 빠진 문서가 곧바로 보인다.

| 순서 | 문서 | 답하는 질문 | 없으면 |
|---|---|---|---|
| 1 | `spec-{feature}.md` | **무엇을** 만드는가 (범위 + «안 하는 것») | 범위가 매 회의마다 다시 열린다 |
| 2 | `*.jsx` | **어떻게 보이는가** (실측·토큰) | 말로 합의한 화면을 사람마다 다르게 상상 |
| 3 | `screen-*.policy.md` | **언제 무엇이** 일어나는가 (조건·상태·에러·역할) | 구현이 매 분기마다 기획자에게 물어봄 |
| 4 | `arch-*.md` | 다른 것과 **어떻게 이어지는가** | 이 기능은 맞는데 옆 기능과 모순 |
| 5 | `TC_*.md` | **됐는지 어떻게 아는가** | 「된 것 같다」로 끝나고 회귀가 안 잡힘 |

**1→5 는 «바꾸기 비싼 것 → 싼 것» 순서.** 거꾸로 시작하면(TC부터, 화면부터) 앞이 바뀔 때마다 뒤를 통째로 다시 쓴다.

### 각 벌에서 깨지는 지점

| 벌 | 실제로 하는 일 | 여기서 깨진다 |
|---|---|---|
| spec | 절마다 **결정 출처**(회의·티켓·누구의 판단) 부착, 버전 이력 한 줄 | 버전 번호 충돌 — 이력표는 최신이 위. 검색 결과만 보고 번호 정하면 중복. **이력표 머리를 직접 열 것** |
| jsx | **대응 앱 화면 URL 먼저 특정** → 실측 → 토큰만(hex 금지) → 헤더에 근거·계측일 | 앱에 없는 신규 화면이라고 새 시각 언어를 만드는 것 · **bypass 함정**: `python3`·`sed`·heredoc 으로 고치면 편집 도구 감시만으로는 가드가 안 뜬다 → **셸 명령까지 감시 대상** |
| policy | 화면 기획과 **항상 동시에**. 「잘 썼다」가 아니라 **항목 충족**으로 판정 | 나중에 쓰기로 하면 그림만 남고 그때의 조건이 사라짐 |
| arch | **영향 표 조회** → 고정 순서 연쇄 → 착수 전 한 줄 확인 | 순서 건너뛰기 · 중복 반영 · 뒤처진 채 푸시 |
| tc | 정책 항목 1개 = TC 1개. **값이 아니라 불변식** | 형태로 적으면 그 형태만 확인하고 통과 → 같은 규칙 깨는 **다른 형태**에 도달 |

**정책서 필수 7항목** (+ AI 기능이면 4항목)
```
1 화면 접근 조건 — 권한 + 상태 «둘 다»
2 모든 UI 요소의 표시/비표시 조건
3 로딩 · 빈 상태 · 에러 상태 렌더링 규칙
4 모든 버튼의 트리거 → 결과
5 API 호출 시점 · 파라미터 · 실패 처리
6 역할별 뷰 차이
7 엣지케이스 3개 이상
+ AI: 생성 버튼 활성 조건 · 확인/미확인 전환 · 실패 fallback · 데이터 출처 표시
```

## B-4. 기반 문서 6종 — 앞 문서가 남긴 질문에 뒤 문서가 답한다

기능마다 쓰는 다섯 벌과 달리 **제품 전체에 하나씩만** 있다. 기능 기획은 여기에 «등재»되는 방식으로 합류.

```
① 유저 저니 맵   누가·무엇이 아픈가   ─ 페인·순간 ─▶
② 유저 플로우    어떤 경로로 움직이나  ─ 화면목록·분기 ─▶
③ IA            어떤 구조로 놓이나   ─ 계층·경로 ─▶
④ 와이어프레임    대충 어떻게 생겼나   ─ 배치·구성요소 ─▶
⑤ 데이터 인벤토리 무슨 데이터를 만지나  ─ 필드·민감도 ─▶
⑥ AI 데이터 스펙  AI는 뭘 받고 뭘 내나
```

**거꾸로 만들면**: IA부터 그리면 «이 메뉴가 왜 있는지»를 아무도 답할 수 없고, 데이터 인벤토리부터 만들면 **안 쓰는 필드를 정성껏 정의**하게 된다.

핵심 규칙 몇 개:
- **유저 플로우** — 정상 경로만 그리면 절반. **실패·만료·재시도 분기를 같은 그림에** 넣는다 → 이게 나중에 정책서 엣지케이스와 TC가 된다 (매번 새로 발명하지 않는다)
- **와이어프레임** — 실측을 넣지 않는다. 넣기 시작하면 JSX와 **두 벌의 진실**이 생긴다
- **데이터 인벤토리** — 수집 방식 3분류(직접입력/자동수집/AI생성). **«민감» 칸 하나가 권한·감사·삭제 정책 셋을 끌고 온다** → 비워두지 않는다
- **AI 데이터 스펙** — 공통 규약을 맨 앞에(수동 트리거만 · 미확인/확인 전환 · fallback 필수 · 모델 라우팅 · 프롬프트 버전 관리). 구현과 대조 못 한 항목은 **«미대조»로 박아둔다 — 추측해서 고치지 않는다. 틀린 확신보다 표시된 공백이 낫다**

### 원칙 05 — 안 센 값을 적지 않는 법 (가장 여러 얼굴로 데인 병)

> AI로 일할 때 특히 잘 난다 — **그럴듯한 문장이 관측처럼 읽히기 때문.**

| 병 | 적힌 것 | 실제 |
|---|---|---|
| 안 센 값 | 「컨트롤러 46개 전수 확인」 | 세어본 적 없음. 실제 58개 |
| 좁은 검색 | 「잔존 0건」 | `workspaces/:wsId` 로만 검색. 변종이 16파일에 남아 있었음 |
| 어긋난 단위 | 「읽는 유일한 폴더」 | **엔티티 전체**를 읽는 유일한 폴더. 필드 단위로는 다른 폴더도 읽음 |

→ 「전수 확인」류 주장에는 **세는 법 셋**을 함께 적는다: **무엇을 · 어느 단위로 · 어떻게(도구·검색어)**

> 세는 값과 세는 법 중 오래 쓰이는 건 **세는 법**이다 — 값은 다음 커밋에 낡는다.

### 원칙 06 — 50%에서 끊는다

```
컨텍스트 50% 도달 ──▶ 하던 한 가지만 마감 ──▶ 인계 카드 ──▶ /clear ──▶ 새 세션이 카드만 이어받음
```

**50%인 이유**: 아직 스스로 무엇을 넘길지 고를 수 있는 시점. 자동 압축은 아무 데서나 끼어든다.

| 카드에 쓰는 것 | 쓰지 않는 것 |
|---|---|
| 지금 하던 일 — 끝나지 않은 **한 가지** | 끝난 일 · 오늘 한 일 목록 |
| 다음 한 걸음 — 처음 할 **행동 하나** | 계획 전체 · 로드맵 |
| 근거 — 커밋 SHA · 「확인: … (날짜)」 | 기억으로 쓴 상태 주장 |
| 넘기지 않는 것 — 일부러 뺀 것 | |

**끝난 일은 넘기지 않는다.** 넘겨야 할 만큼 중요하면 그건 카드가 아니라 **커밋·문서·티켓 코멘트**에 있어야 한다.

# C. 우리 리포에 바로 적용할 것

## C-1. `meeting_minutes` 에 «멈춤 게이트» 추가 (최우선)

우리가 만든 파이프라인은 덱의 B-1과 거의 같은데 **한 칸이 없다.**

```
현재  녹음 ─▶ STT ─▶ Claude 추출 ─▶ md/html/json ─▶ 드라이브
덱     녹음 ─▶ STT ─▶ Claude 추출 ─▶ ■ 번호로 제시·사람이 고름 ─▶ 문서 반영
```

없으면 «회의에서 나온 말»과 «결정»이 구분되지 않는다. 추가할 것:
- `--review` 모드: `action_items` / `decisions` 를 번호로 출력하고 종료
- 사람이 고른 번호만 남겨 확정본 재생성 (`--accept 1,3,5`)
- 확정 전 산출물은 `draft/` 로 분리

## C-2. `unclear_notes` 를 «미확인 / 미조사»로 분리

지금은 담당자·마감이 없으면 `null` 하나로 끝난다. 덱의 구분을 넣으면 받는 쪽 왕복이 사라진다.

```python
owner_status: Literal["confirmed", "unassigned_in_meeting", "not_investigated"]
# unassigned_in_meeting = 회의에서 안 정해짐 (= 미확인)
# not_investigated      = 녹취에 있을 수 있는데 못 찾음 (= 미조사)
```

## C-3. CLAUDE.md 4층 세팅 (아직 0층)

현재 `AI_hub` 에는 CLAUDE.md 가 없다. 덱 기준 3층이 비어 있는 상태.

```
1층 ECC              /plugin install ecc@ecc          ← 아직 안 함
2층 ~/.claude/CLAUDE.md   개인 작업 방식              ← 메모리는 있으나 CLAUDE.md 없음
3층 AI_hub/CLAUDE.md      리포 규칙 + 프로젝트 인덱스  ← 없음 (최우선)
4층 .claude/hooks/        검사 코드                   ← 없음
```

3층부터. 프로젝트 2개(`hospital_rag_assistant`, `office_automation`)의 진입 문서를 3~4줄로 지정.

## C-4. 첫 훅 3개 후보 — 우리가 이미 데인 것에서

덱의 원칙: **미리 설계하지 않는다. 데인 것에서 만든다.** 이 세션에서 실제로 데인 것들:

| 사고 | 훅 후보 | 지점 |
|---|---|---|
| 진행상황.md를 시키지 않은 분량으로 장황하게 씀 | `doc-length-guard` — 지정 파일이 N줄 초과하면 반려 | PreToolUse (Write) |
| heredoc 이 유니코드 때문에 실패 → 파일이 안 만들어졌는데 `echo ok` 로 성공처럼 보임 | `write-verify-guard` — 파일 쓰기 후 존재·크기 확인 | PostToolUse |
| 콘솔 cp949 로 한글 깨짐 → 출력을 잘못 읽을 위험 | SessionStart 에서 `PYTHONIOENCODING=utf-8` 주입 | SessionStart |

## C-5. 컨텍스트 50% 인계 카드 — 아까 물어본 compact 문제의 답

`--autocompact` 로 창을 늘리는 것보다 덱의 방식이 낫다. **50%에서 내가 끊는다.**

```
/context 로 확인 ─▶ 50% 넘으면 하던 한 가지만 마감 ─▶ 인계 카드를 진행상황.md 에 append ─▶ /clear
```

카드에 «끝난 일»을 쓰지 않는 게 요점. 끝난 일은 이미 docs·커밋에 있다.

## C-6. 병원 프로젝트에 그대로 겹치는 것

| 덱 | 병원 프로젝트 |
|---|---|
| 원칙 05 «안 센 값을 적지 않는다» | 우리 `quote` 강제 · `numeric fidelity exact match` — **같은 병에 대한 같은 처방** |
| «형태가 아니라 불변식으로» | 금칙어 정규식(형태)만으로는 부족 → entailment(조건)로 잡는 이유 |
| «미대조로 박아둔다. 추측해서 고치지 않는다» | abstain. **틀린 확신보다 표시된 공백이 낫다** |
| 정본(SSOT) 지정 → 가드가 그 파일만 검사 | `struct` 정형 테이블을 숫자의 유일 원천으로 둔 것 |
| 정책서 필수 7항목 = 항목 충족으로 판정 | 평가 기준 C1~C7 을 DB에 두고 채점하는 것 |

병원 프로젝트 설계와 이 덱은 **독립적으로 같은 결론에 도달했다.** 그래서 서비스팀장님께 설명할 때 이 덱의 언어를 그대로 쓸 수 있다.
